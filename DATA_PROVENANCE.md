## 2. Database Schema — Verified by Direct Inspection

All information in this section was obtained by running SQLite queries against `demo_data/healthcare.db`.

### 2.1 Tables

| Table | Rows | Notable column types | Source |
|---|---|---|---|
| `raw_patients` | 55,500 | All 15 columns TEXT (including `age` and `billing_amount`) | Hackathon dataset |
| `staging_patients` | 55,500 | Same 15 columns plus 6 added columns (`gender_clean`, `blood_type_clean`, `condition_clean`, `admission_type_clean`, `test_results_clean`, `pipeline_status`) | Hackathon dataset |
| `mart_billing` | 55,500 | `billing_amount` REAL; `length_of_stay_days` untyped; `doctor`, `room_number` excluded | Hackathon dataset |
| `mart_demographics` | 55,500 | `age` INT; `doctor` excluded; `test_results` column present (un-normalised value) | Hackathon dataset |

### 2.2 Views — exact SQL from `sqlite_master`

**`v_staging_from_raw`**
```sql
SELECT *, 
  LOWER(TRIM(gender)) AS gender_clean,
  LOWER(TRIM(blood_type)) AS blood_type_clean,
  LOWER(TRIM(medical_condition)) AS condition_clean,
  LOWER(TRIM(admission_type)) AS admission_type_clean,
  LOWER(TRIM(test_results)) AS test_results_clean,
  'staged' AS pipeline_status
FROM raw_patients
```

**`v_billing_from_staging`**
```sql
SELECT name, hospital, insurance_provider,
  admission_type_clean AS admission_type,
  CAST(billing_amount AS REAL) AS billing_amount,
  date_of_admission, discharge_date,
  ROUND(JULIANDAY(discharge_date) - JULIANDAY(date_of_admission), 1) AS length_of_stay_days,
  medication, pipeline_status
FROM staging_patients
```

**`v_demographics_from_staging`**
```sql
SELECT name,
  CAST(age AS INTEGER) AS age,
  gender_clean AS gender,
  blood_type_clean AS blood_type,
  condition_clean AS medical_condition,
  hospital,
  test_results_clean AS test_results,
  pipeline_status
FROM staging_patients
```

> Note: `mart_demographics.test_results` was populated from `staging_patients.test_results` (un-normalised), not from `test_results_clean`. The view `v_demographics_from_staging` selects `test_results_clean`. This inconsistency between the mart table and the view is the factual basis for Conflict 5.

## 4. The Five Conflicts — Detailed Provenance

### Conflict 1 — `billing_amount` (CRITICAL)

| Question | Answer |
|---|---|
| Did this anomaly exist naturally in the official dataset? | **Yes.** 1,215 rows with negative `billing_amount` confirmed by direct SQL on `raw_patients` |
| Does the hackathon scenario documentation identify this as a conflict? | **Not established.** The hackathon materials were not reviewed during this session |
| Did Rosetta infer this conflict? | **Yes.** Rosetta authored two `MetricDefinition` objects — one for `clinical_team` (no sign constraint) and one for `finance_team` (positive-only) — and fed them to `detect_conflicts()` |
| Did Rosetta add any definition, rule, anomaly, or lineage edge? | **Yes — definitions and rules only.** Rosetta wrote both `definition_text` strings and both `sql_logic` strings. No anomaly rows were inserted into the database. No new lineage edges were added beyond the `_DOWNSTREAM` graph Rosetta maintains |
| Exact evidence used to detect it | `logic_sim` score below threshold (two conflicting SQL predicates: `FROM raw_patients` vs. `FROM mart_billing WHERE billing_amount > 0`); confirmed by `neg_billing = 1,215` from `_read_stats()` |
| Severity source | `_row_evidence` override in `healthcare_demo.py`: severity set to `critical` based on 1,215 affected rows; `blast_radius` = max(downstream graph size, 1215 // 100) = 12 |
| Financial figure ($28,478,287) | Computed by Rosetta's `_read_stats()` via `SUM(ABS(billing_amount)) FROM mart_billing WHERE billing_amount < 0`; the underlying data is from the hackathon DB |

### Conflict 3 — `patient_age` (HIGH)

| Question | Answer |
|---|---|
| Did this anomaly exist naturally in the official dataset? | **Yes.** 832 rows with `CAST(age AS INTEGER) < 0 OR > 120` confirmed (416 negative ages, 416 ages above 120; range −88 to 285) |

| Severity source | `_row_evidence` override: `high` |
| Correction note | Earlier Rosetta-authored text incorrectly described ages ranging to "285" as biologically impossible upper bound. The confirmed range from the DB is −88 to 285. Both ends fall outside the 0–120 valid range |

### Conflict 5 — `test_results` / `test_results_clean` (MEDIUM, hidden synonym)

| Question | Answer |
|---|---|
| Did this anomaly exist naturally in the official dataset? | **Yes — the two columns are present in the hackathon DB.** `raw_patients.test_results` stores mixed-case values (`'Normal'`, `'Abnormal'`, `'Inconclusive'`); `staging_patients.test_results_clean` stores lowercase equivalents (`'normal'`, `'abnormal'`, `'inconclusive'`). The normalisation view `v_staging_from_raw` creates `test_results_clean` via `LOWER(TRIM(test_results))`. `mart_demographics` was populated with the un-normalised `test_results` value (confirmed by table DDL), while `v_demographics_from_staging` selects `test_results_clean` |
| Does the hackathon scenario documentation identify this as a conflict? | **Not established** |
| Did Rosetta infer this conflict? | **Yes.** Rosetta identified the two columns as a hidden synonym by assigning them the same metric name `test_results~test_results_clean`. `detect_conflicts()` detected it as kind `hidden_synonym` based on high `name_sim` combined with structural difference |
| Did Rosetta add any definition, rule, anomaly, or lineage edge? | **Yes — definitions and column pairing only.** The two columns pre-exist. Rosetta authored the definition texts and created the `test_results~test_results_clean` compound metric name to express the synonym |
| Exact evidence used to detect it | High `name_sim` between `test_results` and `test_results_clean`; confirmed by distinct-value queries showing case-only difference between the two columns |
| Severity source | `_row_evidence` override: `medium`, `blast_radius = max(downstream, 55500 // 100)` = 555 (all rows affected) |
